# Design v0

## Goal

Know early when a project tracked in Enji Guard is going badly, and tell the
team in Telegram without anyone having to look.

## Flow

```
timer -> poll Guard -> rules -> (findings?) -> Claude triage -> dedup -> Telegram
```

1. **Poll.** Fetch the current state of every project from Enji Guard through its
   MCP server (deterministic client calls, no LLM).
2. **Rules.** Pure functions over the snapshot (and the previous one) produce
   typed `Finding`s: what, which project, severity, evidence.
3. **Triage.** Only when findings exist, Claude gets the findings plus the
   relevant snapshot slice and returns a short per-project summary, probable
   cause and priority. Output is schema-validated; on failure the alert goes out
   with rule text only.
4. **Dedup.** A finding already alerted and still unresolved is not re-sent
   (key = project + rule + subject). Recovery can emit a single "resolved" note.
5. **Alert.** Post one message per run to the Telegram group via the bot.

## Open questions (need the operator)

- ASSUMPTION: Guard is reachable as an MCP server (configured in Claude, not yet
  in this environment). Exact tool names, auth and data shape are unknown until
  the connection details are provided; the rules and the snapshot model are
  drafted against that data, not guessed.
- Which problems matter (first rule set): to be listed from real Guard data.
- Schedule and quiet hours; Telegram chat id and bot token (`.env`).
- Whether Claude is called via `claude -p` or the Agent SDK.
