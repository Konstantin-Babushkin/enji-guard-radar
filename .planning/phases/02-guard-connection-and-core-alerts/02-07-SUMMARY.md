# 02-07 Summary: poll health and ops chat

- `health.py` (core, pure): `classify_poll`, `advance_health`, `mark_ops_delivered`, `ops_message` and the `PollOk`/`PollFailed`/`Outage`/`Recovered`/`NoOpsAction` types. One outage message when K failed polls in a row are reached, one recovery after the first good poll, a cause change inside an outage sends nothing. The marks (`outage_reported_at` set or cleared) are applied only after the ops chat acknowledged the message, so an unacknowledged message is sent again next run.
- `guard.py`: `GuardDataError`, `ListingUnknown` and `ProjectUnknown` carry `cause` and `auth_kind` (defaults DATA and None), copied from `GuardCallError.cause` and `GuardAuthError.kind`.
- `config.py` and `config/radar.example.yaml`: `ops.failures_before_alert` (default 3, 1..20).
- `pipeline.py`: the Guard-unavailable path saves state, so the count advances across timer runs. A failed poll (listing unknown, or every active project unknown) ends the run with `GUARD_UNAVAILABLE` and `RunReport.poll_failed`; `RunReport.ops_sent` counts acknowledged ops messages. Without `TELEGRAM_OPS_CHAT_ID` an ERROR log names the variable and nothing is marked; a dry-run prints the would-be message and writes nothing (its notifier never returns `Delivered`).
- Tests: `tests/test_health.py` (guard cause rows, classification, state machine, wording, exhaustive sequence property), `tests/test_pipeline_ops.py` (tracer through `cli.main`, failed ops send, no ops chat, dry-run, mixed poll, K = 1, auth outage, ordering, log lines), config rows, and the two listing-failure tests now expect a saved health block.
- Decision: `last_success_at` is stamped when a streak of failures ends, not on every healthy poll. The plan said to stamp it on every good poll, but `tests/test_state_v2.py` (outside this plan's file list) requires an empty health block after a clean run.
- Not done here: the live failure drill and tuning of K (plan 02-11), the doctor line for unevaluated projects (02-08). No human checkpoint task in this plan.
