<objective>
Give the radar a memory for High findings (D-01): State schema 2 with per-(project, repo, audit type) run history keyed by Guard task_id, a pure fold that opens an episode at the first High run and clears it only after M clean runs (RULE-09), a per-run re-arm that plans an alerted or baselined High condition again whenever its count rises between two consecutive completed runs (STATE-07, D-06), and the poll-health block that plan 02-07 fills. A Phase 1 state file keeps working (pure 1 -> 2 migration).

Purpose: every later High-count rule and the ops-chat logic read this state. Getting identity (task_id, never poll), debounce and re-arm right here prevents both double alerts and silent misses.
Output: `ledger.py` schema 2, new core module `high_history.py`, the tracer and table tests, and the small updates of Phase 1 tests that pinned schema_version 1.
</objective>

## Decisions recorded here

- D-01 (locked, settled in CONTEXT.md, rated costly there): history is accumulated in state, counted by Guard task_id. This plan fixes its on-disk shape. No new checkpoint: the decision is settled and nothing is deployed yet (state exists only from fixture runs); the 1 -> 2 migration is a pure function, so a later shape change stays a migration, not a reset.
- D-06 (locked, RESOLVED in 02-RESEARCH.md Open Question 1): re-arm is per run. `reconcile` compares the new count with the count stored on the record at its previous evaluation. That stored count is the previous completed run's High count, because plan 02-04 emits every open series on every evaluated poll (from stored history when the newest report is unknown). 3 -> 2 -> 3 alerts again. So does 3 -> 0 -> 3 inside the M-clean-run debounce: RULE-09 keeps the episode and the condition (no resolve, age kept), and D-06 sends the rise. Research Pattern 5's high-water field (`alerted_count`) and peak rule are superseded and not built. ConditionRecord keeps its schema-1 fields, so the 1 -> 2 migration adds only `histories` and `health`. Reversible: one branch in `reconcile`.
- A baselined condition keeps its count, so a project's first poll stays silent (STATE-05) and a later rise above that count re-arms it.
- Every Phase 1 record has count None (stale and never-ran carry no count), so the per-run rule can never re-arm a migrated record.
- PollHealth lands in schema 2 now (data only, all defaults) so that the on-disk format is decided once; `advance_health` and its use are plan 02-07.
- `HISTORY_WINDOW` is a constant (20), not config: it only bounds state size and must stay at least M (config allows M up to 10, plan 02-02) and the Phase 3 recurring N.
