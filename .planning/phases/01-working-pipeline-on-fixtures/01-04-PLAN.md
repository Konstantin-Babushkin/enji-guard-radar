Telegram Bot API facts, checked on core.telegram.org/bots/api on 2026-11-16:
- Requests are `https://api.telegram.org/bot<token>/METHOD_NAME`, so the token is in the URL path.
- The response is JSON with a Boolean `ok`, an optional `description`, `result` on success, and an `error_code` on failure. The page says error_code's "contents are subject to change in the future".
- `ResponseParameters.migrate_to_chat_id`: "The group has been migrated to a supergroup with the specified identifier" (may exceed 32 bits). `ResponseParameters.retry_after`: "In case of exceeding flood control, the number of seconds left to wait before the request can be repeated".
- `sendMessage`: `chat_id` is Integer or String; `text` is "1-4096 characters after entities parsing"; `parse_mode` "HTML". In HTML style, `<`, `>` and `&` that are not tags must be written as `&lt;`, `&gt;`, `&amp;`.

## Decisions recorded here

- Transport: stdlib `urllib.request` behind the `HttpTransport` boundary. Research (.planning/research/STACK.md) recommended `httpx2` and `pydantic-settings`. This plan uses the standard library and a small strict `.env` reader instead: neither package has a Package Legitimacy Audit, AGENTS.md says "simplest thing that works", and urllib does not log request URLs. Swapping the transport later is a one-class change behind `HttpTransport` (reversible).
- Parse mode is HTML (not MarkdownV2), with escaping owned by `messages.escape` (plan 01-02).
- Same-wave compatibility with plan 01-05: these tests never call `messages.render_messages`, whose signature plan 01-05 changes (collapse_above becomes a required keyword). They build messages from `messages.render_alert(alert)`, which keeps its signature, so `make verify` stays green whichever wave-3 plan merges first. Plan 01-05 also changes render_alert's output for unusual names (clean_name flattening and truncation), so these tests assert the payload shape only: the URL, the exact key set {chat_id, text, parse_mode}, the chat_id type, parse_mode "HTML", a non-empty text, and the absence of the token. They never compare the rendered text.

## Flagged assumptions (carried, not settled here)

- ASSUMPTION: Telegram answers 401 for a wrong but well-formed token and 404 for a malformed token path, and 403 when the bot was removed or blocked. error_code contents are "subject to change" per the API page, so classification uses `parameters` first and the status codes second. The live check in plan 01-07 exercises the wrong-token path for real.
- ASSUMPTION: a Telegram bot token has the shape `<6 or more digits>:<30 or more of A-Z a-z 0-9 _ ->`. The exact value from the environment is always masked as well, whatever its shape.

telegram.py (a shell module; the architecture test allows its urllib and time imports). HttpResponse is a frozen dataclass (status: int, body: bytes). TransportFailure(Exception) carries kind: Literal["timeout", "network"] and a short message that never contains the URL. HttpTransport is a Protocol with post_json(self, url: str, payload: Mapping[str, object], timeout_s: float) -> HttpResponse, raising TransportFailure. UrllibTransport.post_json builds urllib.request.Request(url, data=json.dumps(payload).encode("utf-8"), headers {"Content-Type": "application/json"}, method="POST"), calls urllib.request.urlopen(request, timeout=timeout_s) (call it through the module attribute so tests can monkeypatch it) inside a with block, and returns HttpResponse(status, body). urllib.error.HTTPError becomes HttpResponse(error.code, error.read()), with the error closed. TimeoutError, and a URLError whose reason is a TimeoutError, raise TransportFailure("timeout", "request timed out"); any other urllib.error.URLError and OSError raise TransportFailure("network", "network error: <exception class name>"). Both are raised with "from None", so no chained traceback carries the URL, and default TLS verification stays in place (no custom SSL context).
