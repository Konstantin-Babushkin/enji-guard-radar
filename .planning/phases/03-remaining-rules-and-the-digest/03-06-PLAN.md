<objective>
Write the pure tooling-gap rule (RULE-07, D-10) and teach the Guard reader to say whether a repository's run list was read to its end.

Purpose: SC3 wants a repository with no recent completed run of `audit.dead-code`, `audit.implementation-unification`, `audit.security` or `audit.dependency-hygiene` shown as a tooling gap in the digest only. The reader's run paging stops as soon as no unread run can be newer (a Phase 2 cost decision), and `list_audit_runs` returns only the latest few runs, so "not in this poll's runs" does not prove "no run in 60 days". The rule therefore keeps what the radar has seen, and only calls a gap when it has the evidence (see Notes).
Output: `tooling_rules.py`, `RepoRuns.runs_complete`, tests.
</objective>

## Notes

- Decision rule per (repo, audit type), with `last` = the later of the stored last_completed_at and the newest counting run of that type in this poll (None when neither): a gap needs `last` to be None or at least window_days old; and either `repo.runs_complete` is True or `now - observed_since` is at least window_days. A pair that would be a gap but has neither piece of evidence is `undecided`. ASSUMPTION: this evidence rule is Claude's Discretion in D-10 (the decision states the rule, not how Guard's truncated run list is bridged); the first gaps for repositories with long run histories therefore appear window_days after the radar first polled them. docs/ideas gets an item in plan 03-11 about a faster, filtered lookup once the `list_audit_runs` filter argument is verified against the real tool schema (it is not verified here; guard.py marks argument names as ASSUMPTION).
- `observed_since` is set to `now` the first time a pair is seen and never moves. `last_completed_at` only moves forward.
- Paused and excluded projects are not passed in by the pipeline (SRC-05), so this module has no mode check.
