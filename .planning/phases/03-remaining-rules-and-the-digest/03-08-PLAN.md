## Notes

- Text templates (Claude's Discretion on exact wording; these are the ones the tests pin). Title: "<b>Guard radar weekly digest</b>", with " (k/n)" inside the bold when split. Poll line: "Last successful Guard poll: 2026-11-18 06:00 UTC." Count line: "Open items: N." Unread line: "1 project could not be read in that poll." or "N projects could not be read in that poll." Items: "- High: <b>{project}</b>: {N High finding(s)} in {audit type} ({repo}). Seen by the radar since {date} ({N days}).", with " Recurring: High findings in each of the last {n} runs." appended for a recurring series; "- Stale: <b>{project}</b>: no completed Guard run for {N days} (last: {date})." or, for a project that never ran, "- Stale: <b>{project}</b>: no completed Guard run found."; "- Low score: <b>{project}</b>: {audit type} score {score}/100 in {repo} (run {date}).", which shows the score and the run date and nothing else (D-08: no threshold, no delta); "- Tooling gap: <b>{project}</b>: no completed {audit type} run in the last {window} days in {repo} (last run: {date})." with "(none seen)" when no run was ever seen. More line: "+3 more open items not shown." ("+1 more open item not shown."). Resolved: "Resolved since the last digest (N):" then "- <b>{project}</b>: High findings in {audit type} are closed." for level "high", "- <b>{project}</b>: no longer stale." for "stale", "- <b>{project}</b>: now has completed Guard runs." for "never_ran", then "+M more resolved." The all-clear line: "<b>Guard radar weekly digest</b>: nothing open. Last successful Guard poll: 2026-11-18 06:00 UTC." Dates are `YYYY-MM-DD` in UTC.
- Interpretation of D-05 and D-09 (flagged for the operator): D-05 lists "open High series" and "recurring series" as two tiers, D-09 says a series is shown once in its worst tier. RULE-08 flags a series whose High count stayed above zero for N runs, and such a series is by construction an open High series, so showing it once in the worse (High) tier leaves the second tier with nothing to hold. The builder therefore keeps four tiers and marks recurring series inside the High tier, which satisfies "once per series" and "worst first" and loses nothing; if the operator wants recurring series ranked below fresh High series instead, that is a one-function change in `build_digest`.
- Sort keys: High: count descending, then age_days descending, then project name casefolded, then key text. Stale: age_days descending with never-ran after the aged ones (the same order `messages.render_messages` uses), then name, then key. Low score: run date ascending, then score ascending, then name, repository id, audit type. Tooling gap: never-seen first, then the oldest last run, then name, repository name, audit type.
- A resolved item whose project is not in `project_names` (it was not read in this poll) prints under the unnamed-project fallback; the group is told counts, never an id.
- The poll time is the time of the poll the caller just completed; the digest is only ever built from a successful poll (plan 03-11 defers otherwise, D-03).
